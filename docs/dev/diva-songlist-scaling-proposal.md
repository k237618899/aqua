# DIVA 歌曲列表 900+ 擴展穩定性優化提案

## 背景

在歌曲數量提升到 900 首以上後，伺服器出現扛不住、偶發錯誤、回應不穩等問題。依目前程式結構判斷，問題不是單一點故障，而是由「大資料量回應 + 重複運算 + 日誌 I/O + DB 型態限制」疊加造成。

本提案目標：

1. 先止血，快速降低故障率與尖峰延遲。
2. 再優化，降低 CPU、I/O 與資料庫壓力。
3. 最後做結構升級，讓未來 1000+ / 1500+ 曲仍可維持穩定。

## 目前可確認的高風險點

### 1) pv_list 回應全文寫入 log

現況：pv_list handler 會將整段回應字串寫入 info log。

風險：

- 歌曲越多，字串越大，磁碟 I/O 與字串處理成本顯著上升。
- 同時多機台請求時，log 寫入會放大延遲與抖動。

### 2) 每次請求都重新組裝完整 pv_list

現況：每次請求都重新查四個難度並 URI encode 後拼接字串。

風險：

- 高頻請求時重複做大量 CPU 工作。
- 產生較高 GC 壓力。

### 3) musicList 直接回 Entity 全量資料

現況：API 直接回傳 Pv Entity，資料量大時序列化成本增加。

風險：

- 可能拉高序列化時間與記憶體峰值。
- 關聯欄位或 lazy 行為在高量時可能放大開銷。

### 4) 回應壓縮未明確啟用

現況：設定中未見 server 壓縮項。

風險：

- 大 payload 在網路品質一般時容易造成延遲與重試。

### 5) SQLite 在高併發長期擴展的天花板

現況：預設使用 SQLite。

風險：

- 在多連線與較高請求密度下，吞吐與穩定性不如 MariaDB/MySQL。

## 優化策略總覽

分三階段實施：

- Phase A: 快速止血（1-2 天）
- Phase B: 性能強化（2-5 天）
- Phase C: 架構升級（中期）

---

## Phase A: 快速止血（優先級 P0）

### A1. 禁止記錄 pv_list 全文

作法：

- 將目前完整 response logging 改為摘要 log。
- 只記錄：request id、總長度、easy/normal/hard/extreme 筆數、處理耗時。

預期收益：

- 立刻下降磁碟 I/O 與 log 造成的阻塞。
- 通常是最容易見效的一步。

回滾：

- 可透過 log level 或單一 commit 回退。

### A2. 為 pv_list 增加記憶體快取

作法：

- 建立 pv_list 內容快取（字串與最後更新時間）。
- 讀請求直接回快取。
- 只有在管理端更新曲目時才失效並重建。

預期收益：

- 將「每請求重算」降為「資料變更時重算」。
- 在多機台反覆拉資料場景下收益顯著。

回滾：

- 保留開關參數，可快速切回現有路徑。

### A3. 開啟 HTTP 壓縮（至少 gzip）

作法：

- 只針對大型文字回應（例如 musicList、pv_list）啟用壓縮。

預期收益：

- 降低傳輸時間與網路抖動造成的超時重試。

回滾：

- 設定即可關閉。

---

## Phase B: 性能強化（優先級 P1）

### B1. musicList 改為 DTO / Projection

作法：

- 不直接回 Entity。
- 改為只回前端/機台真正需要的欄位。

預期收益：

- 減少序列化成本與記憶體占用。
- 降低潛在 lazy loading 風險。

### B2. 查詢優化與索引確認

作法：

- 確認 diva_pv_entry 的索引可支援 difficulty 條件查詢。
- 視 DB 引擎補充必要複合索引。

預期收益：

- 降低四次難度查詢在大資料量下的延遲。

### B3. 加入請求級性能指標

作法：

- 對 musicList 與 pv_list 打點：QPS、P50/P95/P99、payload 大小、錯誤率。

預期收益：

- 可量化每次優化效果，避免感覺式調整。

---

## Phase C: 架構升級（優先級 P2）

### C1. 資料庫遷移到 MariaDB/MySQL（建議）

作法：

- 生產環境改用 MariaDB 或 MySQL。
- SQLite 保留給單機/測試。

預期收益：

- 更高併發穩定度。
- 更好的查詢計劃與連線管理。

### C2. 歌單更新流程標準化

作法：

- 制定「加歌」流程必填檢查（pv_info + pv_entry 四難度一致性）。
- 避免只更新部分表導致機台與 UI 資料不一致。

預期收益：

- 降低資料品質造成的隱性 bug。

## 可能根因對照表

| 現象 | 可能根因 | 優先處理 |
|---|---|---|
| 歌曲數高時卡頓、超時 | 大回應全文寫 log + 重複組包 | P0 |
| 多機台同時請求時不穩 | 無快取 + SQLite 併發限制 | P0/P2 |
| 偶發資料不完整相關錯誤 | 加歌流程未保證多表一致 | P1/P2 |
| 網路環境稍差就異常 | payload 大且未壓縮 | P0 |

## 風險與注意事項

1. 機台協議相容性：

- 不可改動 pv_list 的資料格式與分隔規則。
- 優化只能改生成方式，不改協議內容。

2. 快取一致性：

- 必須在管理端更新後精確失效。
- 建議先用簡單可靠策略（更新即全量失效）。

3. 日誌可觀測性：

- 雖然不記全文，但要保留必要摘要與 request id，方便追查。

## 驗收指標（建議）

在 900-1200 首曲目、至少 5 台機台並行下，目標：

1. pv_list P95 延遲下降 50% 以上。
2. musicList P95 延遲下降 30% 以上。
3. CPU 峰值下降 20% 以上。
4. 錯誤率與超時率顯著下降（目標 < 0.5%）。
5. 功能正確性不變（機台可正常收到並解析資料）。

## 建議實施順序

1. A1 停止大回應全文 log。
2. A2 對 pv_list 做快取。
3. A3 啟用壓縮。
4. B1 DTO 化 musicList。
5. B2 索引與查詢優化。
6. C1 規劃 DB 遷移。

## 可立即執行的最小任務包（第一輪）

1. 修改 pv_list 日誌為摘要（含耗時與長度）。
2. 增加 pv_list 快取與管理端更新失效機制。
3. 開啟壓縮並僅覆蓋文字型大回應。
4. 壓測比對 500 / 900 / 1200 首三組數據。

---

若同意此提案，下一步可進入「第一輪最小任務包」實作，先做可快速回滾且高收益的 P0 改動。
